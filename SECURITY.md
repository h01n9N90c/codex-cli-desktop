# Security Policy

## Security Posture of This Repository

**Codex Dual-Lane & Security Kit** (`codex-cli-desktop`) is a local configuration and guardrail toolkit licensed under **Apache License 2.0** (`Copyright 2026 Lê Hoàng Ngọc Tươi`).

* **Zero telemetry / zero remote code execution:** All scripts run 100% locally and never download binaries or transmit data to external servers.
* **Zero secrets committed:** No API keys, OAuth tokens, or personal host configurations are stored in this repository.
* **4-Layer Defense-in-Depth for Codex Agents (with Full Workspace File CRUD & Directory Tree Mastery):**
  1. **Layer 1 — Workspace-Scoped OS Sandbox & Network Isolation (`Full Workspace File CRUD`):** `sandbox_mode = "workspace-write"`, `[windows] sandbox = "elevated"`, outbound shell network disabled by default (`[sandbox_workspace_write] network_access = false`), safe default `approval_policy = "on-request"`, and optional `-UseGitWorktree` / `--use-git-worktree` for OS-enforced write separation between Lane 1 and Lane 2. Inside the trusted project workspace, the agent has unobstructed authority to traverse the entire directory tree (`rg --files`, `git status`, `Get-ChildItem`, `find`) and freely read, create, edit, move, and delete project files while writes outside the workspace remain blocked at the OS sandbox layer.
  2. **Layer 2 — Secret Hygiene, Flexible Dual-Lane Auth (`env_key` + Login), Environment Filtering & File Permissions:**
     * Supports keeping **Lane 1 (`~/.codex`, Codex Desktop)** on the user's Primary Account (`acc chính`) with **100% full authority as before (`toàn quyền như trước`)** — leaving `~/.codex/config.toml` untouched by default (and never injecting restrictive `sandbox_mode` or `network_access = false` into Lane 1) so Codex Desktop has full project authority across the entire directory tree — while **Lane 2 (`~/.codex-official`, Codex CLI)** supports **both ChatGPT/OpenAI OAuth Login (`codex login`) AND API Key / custom gateway routing (`env_key` via `-GatewayTargetLane Lane2|Lane1|Both` / `--gateway-target-lane lane2|lane1|both`)**.
     * Uses `env_key` (never plaintext API keys or `experimental_bearer_token`) in `config.toml` and timestamped backups.
     * Filters sensitive environment variables from sandboxed child shells (`[shell_environment_policy] exclude = ["*KEY*", "*SECRET*", "*TOKEN*", "*PASSWORD*", "*CREDENTIAL*"]`) while the parent Codex process still reads `env_key` seamlessly.
     * Applies POSIX `chmod 600` (with restrictive `umask 077` / `chmod 700` on sensitive directories) on macOS/Linux/WSL, and a **two-step Windows `icacls.exe` sequence** (`/inheritance:d` followed by `/remove:g "CodexSandboxUsers"`) on `auth.json`, `config.toml`, backups, and rollback manifests.
     * **Strongest Secret Hygiene Recommendation:** Where supported by your installed Codex version, configure `cli_auth_credentials_store = "keyring"` so OAuth/login tokens are stored in the OS credential store rather than plaintext `auth.json`, and always supply API/gateway credentials via `env_key`.
  3. **Layer 3 — Starlark Execpolicy Command Firewall (`templates/default.rules`):** Hard-blocks (`decision="forbidden"`) ransomware/system tampering (`vssadmin`, `bcdedit`, `wbadmin`, `diskpart`, `format`), persistence (`schtasks`, `sc`, `reg add/delete/import`), Windows NTFS ACL/ownership/network tampering (`icacls`, `takeown`, `net`, `net1`, `netsh`), remote history force-push (`git push --force`, `git push -f`), and static-analysis-only corpus interpreters & Windows LOLBins (`php`, `ruby`, `perl`, `cscript`, `wscript`, `mshta`, `rundll32`, `regsvr32`, `certutil`, `bitsadmin`, `msiexec`, `wmic`, `Start-Process`/`saps`, `Invoke-Expression`/`iex`), including explicit `.exe`/`.com` and case variants. Prompts (`decision="prompt"`) before `git push`, `git reset --hard`, and `git clean`, while leaving normal directory tree inspection and file CRUD commands completely unobstructed (`matchedRules: []`).
  4. **Layer 4 — Global `AGENTS.md` Guardrails:** Anti-prompt-injection, **Static-Analysis-Only Isolation** (strictly prohibiting execution of untrusted third-party binaries/exploit samples while explicitly authorizing full workspace directory tree mastery and project file CRUD), secret/config isolation, and dual-lane zero-collision discipline.

## Honest Security Boundaries (Kit Guarantees vs. OS & Codex Runtime Limits)

This toolkit hardens local Codex deployments but cannot override OS kernel or Codex runtime behavior outside its control:

* **Windows `CodexSandboxUsers:(OI)(CI)(RX)` directory inheritance & Elevated vs. Unelevated sandbox backends:** Codex's Windows elevated sandbox may grant `CodexSandboxUsers:(OI)(CI)(RX)` (inherited read/execute) on `~/.codex*` directories. Newly created files inside those directories automatically inherit that ACE. The kit's two-step `icacls.exe` strip (`/inheritance:d` then `/remove:g "CodexSandboxUsers"`) removes the inherited read ACE from targeted files while degrading gracefully on fresh machines where the `CodexSandboxUsers` group does not yet exist. Live verification against `codex-cli 0.171.0-alpha.13` with Win32 `AuthzAccessCheck` confirmed that read access for the elevated `CodexSandboxOffline` identity flips from `ReadAllowed=True (Error=0)` to `ReadAllowed=False (Error=5 [ERROR_ACCESS_DENIED])` after `Protect-SensitiveFileAcl`. By contrast, under the **unelevated write-restricted token** Windows sandbox backend (`IsTokenRestricted=True`, Medium integrity, current user SID), live probes confirmed hard OS write isolation (`WRITE_OK` in `<repo>-lane2` vs. `WRITE_DENIED` on the primary repo and `$CODEX_HOME`), but NTFS ACLs that retain current-user `(F)` cannot deny reads under that backend (`Restricted read-only access requires the elevated Windows sandbox backend`).
* **Atomic file replacement resets NTFS file DACLs (Cannot be blocked externally):** Live verification against real `codex-cli 0.171.0-alpha.13` confirmed that when Codex updates `config.toml` (e.g., `codex features enable/disable ...` or UI settings edits) or recreates `auth.json` via atomic temp-file replacement, Windows re-applies inherited parent DACLs (`AreAccessRulesProtected` resets from `True` to `False` and `CodexSandboxUsers:(RX)` returns), which `scripts/doctor.ps1` immediately flags (`kernel_acl=EXPOSED`) and `scripts/setup-dual-lane.ps1 -ReapplyAclOnly` restores in ~1s with bit-identical SHA-256. Because external scripts cannot intercept future writes performed by Codex itself, `Protect-SensitiveFileAcl` is **point-in-time defense-in-depth** — always keep secrets out of plaintext files via `env_key` + `cli_auth_credentials_store = "keyring"`, audit with `scripts/doctor.ps1`, and re-lock with `-ReapplyAclOnly`.
* **Hard Fail-Closed Worktree Isolation & Windows 8.3 Short-Path Canonicalization:** When `-UseGitWorktree` / `--use-git-worktree` is enabled, the generated Lane 2 CLI wrappers (`codex` / `codex-official`) switch `cwd` from the primary repo root **and any nested subdirectory** into the matching worktree subdirectory (or worktree root), verify `cwd` post-`cd`, and **fail closed (`exit 1`, refusing to execute `codex`)** if the worktree directory is missing/deleted, replaced by a regular file or symlink, or if `cd` fails — never silently falling back to the primary repo. Setting `CODEX_NO_AUTO_WORKTREE_CD=1` skips auto-`cd` **only**; Guard 2 still scans and blocks `-C`, `-C=`, `-C<path>`, `-C"<path>"`, `--cd`, `--cd=`, `--add-dir`, and `--add-dir=` targeting the primary repo fail-closed. On Windows, scripts, `.cmd` wrappers (via runtime `%%~fs`), and tests canonicalize paths with Win32 `GetLongPathNameW` so 8.3 short aliases (e.g., `RUNNER~1`, `PROGRA~1`) cannot evade worktree guards or cause path mismatches. Codex Desktop UI workspace attachments or custom non-CLI launch paths still require testing against your live Codex Desktop build.
* **Crash-Safe Incremental Rollback Journal, Link Ownership & Fail-Closed Preflight (v1.3.1):** Both `setup-dual-lane.ps1` (`.rollback/latest.json`, `Completed: false -> true`) and `setup-dual-lane.sh` (`.rollback/latest.tsv`, `# status=in-progress -> complete`) persist rollback manifests atomically **after every tracked mutation** (junction/symlink, file backup/write, launcher install), so interrupted mid-install runs recover cleanly via `restore-original.*` with byte-exact SHA-256 verification, zero orphaned junctions/symlinks, and preservation of untouched pre-existing user launchers (`doctor.*` also includes a read-only `Rollback Journal` health check). In v1.3.1, rollback introduces **deterministic link ownership** (`SharedLinkRecords` / `L` rows) to track whether each junction/symlink was created by the kit or existed beforehand, ensuring pre-existing user links are preserved untouched upon rollback. Directories are restored strictly from the exact recorded `BackupDirPath` / `dir_bkp` rather than wildcard-sorting `.backup-*` directory names. Furthermore, preflight validation is strictly **fail-closed**: if any required backup is missing and target is not already in its original state, rollback halts immediately with `exit 1` **before** detaching any junction/symlink or modifying any file on disk. On macOS/Linux/WSL, column 5 of `.rollback/latest.tsv` records standard POSIX permission bits (`000`–`777`) and `restore-original.sh` restores exact modes (e.g., `0755` vs `0700`, `0644` vs `0600`) while rejecting special SUID/SGID/sticky bits (`1xxx`/`2xxx`/`4xxx`) from tampered manifests; non-mode attributes such as extended attributes (`xattr`), cross-user ownership, or timestamps are not restored.
* **`execpolicy` prefix-matching scope:** Starlark `prefix_rule` evaluates exact, case-sensitive direct command tokens (`argv[0]`, ...). It does not deeply inspect arbitrary code strings nested inside `powershell -Command "..."`, `cmd /c "..."`, or `bash -c "..."`. Containment always depends on keeping all 4 layers active together.
* **CI vs. Real-Codex test scope boundary:** Cross-platform CI (`ci.yml` — 4 jobs across Ubuntu, macOS, and Windows PowerShell 5.1 & 7+) validates hygiene/line-endings/secret scanning, Starlark AST, fail-closed worktree guards, 8.3 short-path canonicalization, interrupted mid-install recovery, 3x repeated install/rollback loops, and SHA-256/POSIX-mode rollback using mock `codex` binaries. Separate live verification results against real `codex-cli 0.171.0-alpha.13` are documented honestly (including backend limitations) in `docs/REAL_CODEX_CHECKLIST.md`; always re-verify after upgrading your local Codex Desktop/CLI release.
* **Shared brain trade-off:** Linking `sessions/`, `memories/`, `skills/`, and `plugins/` across both lanes means conversation logs are shared between Lane 1 and Lane 2. Never put real secrets into prompts or repositories, and keep confidential codebases on your official OpenAI lane rather than third-party API relays.

## Reporting a Vulnerability

If you discover a security bug, path-traversal flaw, ACL bypass, or secret-leakage issue in any script or template in this repository:

1. **Do not** disclose exploit details or secrets in public issues.
2. Report privately via GitHub **Security Advisories** (Report a vulnerability) on `https://github.com/h01n9N90c/codex-cli-desktop`.
3. Include affected file(s), OS/shell version, reproduction steps, and suggested remediation.
